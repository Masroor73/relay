# Relay - Decisions Log

Context for why Relay is scoped and built the way it is. Read alongside ARCHITECTURE.md and README.md, which describe *what* was built; this describes *why*, including what was deliberately rejected.

## Origin

Relay was scoped as project #1 in a portfolio-building effort, replacing an earlier, much larger project (a fintech fraud-risk platform) that was abandoned in its current form specifically because it tried to cover too much ground in one system: five language runtimes, a Kafka-class broker, multi-tenant RLS, PCI-DSS-adjacent compliance surface, and a four-tier MCP plan, none of which got fully built. The lesson carried forward: prove one capability well and finish it, rather than spec many capabilities and finish none.

Relay deliberately reuses one idea from that earlier project - reliable event ingestion - and stops there, with no fraud/risk decisioning, no regulated data, no multi-service sprawl.

## Core scope decision

Relay is infrastructure, not a product with business logic. It receives, deduplicates, retries, and recovers webhook events. The `orders` table exists only to make processing visibly real (not as a genuine e-commerce feature) - this was a deliberate choice to make a backend-heavy project demoable, not scope creep into building an order system.

## Stack decisions and why

- **Go, not C# or Python** - no honest justification for either in this project; Go fits the concurrent ingestion/processing role directly. C# and Python are reserved for future portfolio projects where they're the actual right answer, not decorative additions here.
- **React, not Vue** - proven experience from a prior team project (V.A.K capstone) means lower friction to actually finish. Vue was considered and deliberately deferred to a future project where trying a second framework is itself the point, not bolted on here for the sake of breadth.
- **Postgres-backed outbox, not Kafka/Redpanda** - avoids standing up a broker before it's justified by actual throughput needs. This is the direct correction of the earlier project's mistake (broker adopted on day one with no justification). Explicitly documented as a Phase II option if throughput ever demands it - not a v1 requirement.
- **One MCP server, three tools** (`list_dlq_events`, `inspect_dlq_event`, `replay_dlq_event`) - chosen because it's a natural byproduct of data already being built for the DLQ, not a new subsystem. Rejected: the four-tier MCP plan from the earlier project, which was scope bloat. **Result:** implemented in Milestone 5 (ENG-42 through ENG-47), all three tools calling `cmd/server`'s existing `/api/*` contract - the same data layer the dashboard uses - rather than reimplementing the underlying queries a second time in TypeScript.
- **`replay_dlq_event` marked `destructiveHint: true`, `idempotentHint: false`** - MCP's own annotation mechanism for signaling a state-changing, non-repeatable action to a client, used instead of inventing a custom confirm-step tool pattern the spec already provides for. `idempotentHint: false` specifically was chosen deliberately, not conservatively: a second replay of the same `dlq_id` genuinely 404s (the row no longer exists), unlike a truly idempotent operation such as a `GET`. Verified via the Inspector's own UI independently surfacing a "DESTRUCTIVE" badge from the annotation, confirming it's read correctly by a real client.
- **v0 (Vercel) for dashboard UI scaffolding** - accelerates admin-UI boilerplate; data-wiring and logic still hand-built. Not something to hide when discussing the project - a legitimate, current workflow. **Result:** v0's default output targets Next.js (its sandbox environment's default, regardless of the target project's real framework) and pulls in shadcn/ui + Base UI as dependencies. Since `apps/dashboard` is Vite, not Next.js, the generated components were rewritten to plain Tailwind v4 + native HTML - same structure, props, and types, without installing a full design-system stack for three tables.
- **Local dev: Docker Postgres (postgres:18-alpine, matching Neon's default version) / Staging+prod: Neon** - avoids Neon cold-start latency during rapid iteration, allows free table resets, works offline. Both environments read the same `DATABASE_URL` contract with no code branching. **Discovered via a real crash-loop on first setup:** the initial Compose config mounted the volume directly at `/var/lib/postgresql/data`, which Postgres 18's image rejects - the image now expects a single mount at the parent `/var/lib/postgresql` directory, placing data in a version-specific subdirectory itself (a convention change from prior major versions, `pg_ctlcluster`-compatible layout). The container entered `Restarting (1)` immediately; the fix was correcting the mount path and clearing the confused volume (`docker compose down -v`).
- **Idempotency enforced via DB `UNIQUE` constraint, not application check-then-insert** - a sequential check has a race window under concurrent delivery. This is why Milestone 2 requires a *concurrent* dedup test (fire the same event twice simultaneously), not just a sequential one - a sequential test would pass even with a broken implementation. **Result:** implemented in Milestone 2 (ENG-19 through ENG-21) and proven, not just asserted - a test firing two simultaneous goroutines against the same event confirmed exactly one success, one duplicate, and one row in each of `events`/`outbox`.
- **`MaxAttempts = 6`, not left implicit** - chosen specifically to give the 5-entry backoff schedule (1s, 5s, 30s, 2m, 10m) an exact 1-through-5 mapping, with the 6th failure triggering dead-letter promotion rather than a 7th retry. **Result:** implemented and proven in Milestone 3 (ENG-27/ENG-28) via a full real end-to-end run through the actual schedule (including the genuine ~10-minute final window), and covered by fast integration tests (ENG-30) that exercise the same logic without waiting through real backoff windows.
- **Outbox row claiming via `SELECT ... FOR UPDATE SKIP LOCKED`, with the lock held for the full claim→handle→delete lifecycle in one `sql.Tx`** - an initial version that only held the lock across the claiming `SELECT` was caught and corrected before merge (ENG-25), since the lock would have released before the handler ran, silently defeating the concurrency guarantee. **Result:** proven via a concurrency test firing two simultaneous pollers against a shared row, confirming exactly one handler invocation.
- **Graceful shutdown implemented for the processor first, `cmd/server` initially not bundled in** - discovered as a real gap in already-shipped Milestone 1 code while building the processor's shutdown handling (ENG-29). Tracked as its own issue (ENG-32, related to ENG-29 and ENG-5) rather than silently folded into ENG-29. **Result:** ENG-32 closed the gap using `net/http.Server`'s built-in `Shutdown(ctx)` - both services now genuinely have shutdown handling.
- **Dashboard API served by `cmd/server`, not a separate service** - `/api/events`, `/api/orders`, `/api/dlq`, `/api/dlq/{id}`, and `/api/dlq/{id}/replay` were added to the existing ingestion service rather than standing up a fourth binary, since `cmd/server` already has the HTTP server, DB connection, and shutdown handling this surface needs. This same endpoint set now also backs the MCP server (Milestone 5) - one API contract, two consumers.
- **CORS scoped to a single configurable origin, not a wildcard** - a wildcard `Access-Control-Allow-Origin` combined with credentialed/authenticated requests (the dashboard sends Basic Auth on every call) is a recognized security anti-pattern, not just unnecessary caution.
- **Dashboard password compared via `crypto/subtle.ConstantTimeCompare`, not `==`** - a plain string comparison short-circuits on the first mismatched byte, theoretically leaking timing information about how many leading characters of a guessed password were correct. Same category of reasoning as choosing Stripe's official SDK over a hand-rolled HMAC comparison in Milestone 1 (ENG-8) - security-sensitive comparisons are not reimplemented casually.
- **Dashboard fetches once on unlock, does not poll** - a deliberate scope boundary for Milestone 4, not an oversight. Data written directly to the database while the dashboard is open requires a manual refresh to appear (confirmed during ENG-38's manual verification). Live-updating is a reasonable future enhancement, not required at single-operator portfolio scale.
- **`apps/mcp-server`'s TypeScript pinned to `^6.0.0`, one version behind the rest of the stack** - `typescript-eslint@8.67.0` does not support TypeScript 7 as of this package's setup (confirmed via the library's own linked tracking issue, not guessed at). A genuine, temporary ecosystem-lag constraint, downgraded specifically for this package rather than left blocking linting entirely. Revisit once upstream support ships.
- **Stripe** chosen as the demo provider - most commonly requested integration pattern, well-documented real signature scheme (used as-is, not simplified).
- **Dashboard auth: single shared password via env var** - appropriate for a single-operator public portfolio deployment; explicitly not multi-user auth, documented as a known limitation rather than a gap to silently fix later.

## Rejected alternatives (considered and explicitly not chosen)

- **A generic SEO/site-audit tool** - rejected because tools like Lighthouse, PageSpeed Insights, and GTmetrix already do this well for free; building another wouldn't demonstrate anything they don't already show better.
- **A full web + mobile app in the same timeframe as this project** - rejected as unrealistic solo in the intended timeframe without the parallelism a team (like the V.A.K capstone's 7 members) provides. Also somewhat redundant with V.A.K, which already demonstrates that capability; Relay was chosen specifically to prove a *different* skill (distributed-systems reliability) that V.A.K's stack didn't touch.
- **Kafka/Redpanda, full multi-tenant RLS, PCI-scoped data handling** - all present in the earlier fintech project; none needed here, and their absence is deliberate, not an oversight.

## Tooling / process setup

- **Linear:** workspace "The Batcave" → team "ENG" → project "Relay" → initiative "Portfolio 2026" (groups all future portfolio projects). Six milestones (Ingestion+schema → Outbox+idempotency → Processor/retry/DLQ → Dashboard → MCP server → Deploy+docs). Labels: Type (feature/bug/chore/docs) × Area (ingestion/processor/dashboard/mcp/infra). 1-week cycles. GitHub repo linked one-way (GitHub→Linear), branch format `username/identifier-title`, magic-word commit linking enabled.
- **Repo:** `relay` on GitHub, public, MIT license, combined Go+Node `.gitignore` (no dead rules for tools not actually used in this project, e.g. no `pgdata/` - Compose uses a named Docker volume, not a bind mount).
- **Package manager:** `pnpm` for both `apps/dashboard` and `apps/mcp-server`, matching the project's own Local Dev-Ex Architecture doc, which already committed to `pnpm` universally - better disk efficiency via a shared content-addressable store, and stricter dependency resolution that prevents the phantom-dependency class of bug npm's flat `node_modules` allows.
- **CI coverage - extended incrementally, each gap tracked rather than left silent:** `build-lint-test` (Go, ENG-16) → `dashboard-build-lint` (ENG-41, after ENG-36 introduced untested JS/TS) → `mcp-server-build-lint-test` (ENG-47, mirroring the same pattern). Each new package's CI job intentionally does not run integration tests requiring a live `cmd/server` instance this job doesn't stand up - documented as a known limitation, with full cross-service CI orchestration scoped as future Milestone 6 work rather than forced into whichever issue happened to introduce the package.
- **Vitest test discovery excluding `dist/`** - default file discovery was silently picking up compiled `dist/tools/dlq.test.js` as a second test suite alongside the real `src/` source, doubling every reported test count (4 real tests reported as 8). Fixed via `vitest.config.ts` excluding `dist/**`, discovered and corrected during ENG-47 rather than left as a confusing, misleading signal.
